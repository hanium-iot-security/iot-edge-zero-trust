# Phase 9 정상 운용 기준 v1

2026/10/9에 예비 수집과 현재 코드로 선택한 개발 기준이다. 식별자는 `phase9-normal-operating-v1`이다. 운영 조건은 우민이 정하고 실장비 근거를 연결하며, 현수는 Rule 경계·공격 회귀, 종민은 공식 편입·품질 검사에 같은 기준을 사용한다. 두 사람의 사전 결재를 기다리는 절차는 두지 않는다. 문제가 발견되면 새 버전으로 수정하고 변경 이유·영향을 남긴다.

이 결정은 아래 동작을 개발에서 허용한다는 뜻이다. 기존 후보 Manifest/QC의 승인 false, Session 108의 개발 이력과 원본은 그대로 보존한다. 특정 Run의 학습 편입·전체 Session 승인을 소급 생성하지 않는다. 이 문서는 현재 Dataset parser가 읽는 승인 문서나 기기 정책 revision을 대신하지 않는다. 식별자는 개발 운영 기준 문서용이며, 공식 편입 계약을 구현하기 전 기존 Dataset의 `normal_policy_version`을 이 값으로 바꾸지 않는다.

## 선택한 운영 조건

| 대상 | 허용하는 동작 | 첫 수집에서의 사용 |
| --- | --- | --- |
| ESP32 P0 | 5,000ms 예약 주기, `device_id`·`sequence`·`uptime_s`만 전송 | 두 ESP32의 기본 본 수집 후보 |
| ESP32 P1 | 한 ESP32의 예약 주기를 4,000~6,000ms에서 변화. P0 필드 유지 | 허용된 개발 Profile. 전체 주기 범위의 QC·회귀가 준비되기 전 본 Train에 포함하지 않음 |
| ESP32 P2 | 한 ESP32가 5,000ms 예약 주기를 유지. `sequence % 3`이 0이면 기본 필드, 1이면 실제 `rssi`, 2이면 실제 `rssi`·`free_heap` 추가 | 허용된 개발 Profile. 혼합 기기·Profile 편입과 별도 그룹 검증 뒤 학습 포함 결정 |
| Pico 기본 | 약 5초 센서 측정·전송. `device_id`·`seq`·`uptime_ms`·`temperature_c`·`humidity_pct`·`pressure_hpa` 유지 | 기본 본 수집 후보. 현재 공개 앱·라이브러리 6파일의 설치 해시 일치 확인 |
| P3·재접속 | 두 변동의 조합 또는 명시적 재접속 | 별도 개발 시험. 현재 안정 정상 학습 범위에 자동 포함하지 않음 |

한 번에 ESP32 한 대만 P1/P2로 바꾸고 다른 ESP32와 Pico는 기본 동작을 유지한다. 현재 시험·복원 기록은 ESP32 2에 대한 것이며 ESP32 1에서 시험 완료했다고 표시하지 않는다. 다음 본 수집은 세 기기 모두 기본 동작부터 준비한다. 이 기준을 정했다는 이유로 펌웨어·정책·Trust·AI 모드를 즉시 바꾸지 않는다.

## 메시지와 크기

Topic은 `iot/{device_id}/sensor`이고 JSON의 ID·등록된 기기·효력 시점의 IP 연결과 일치해야 한다. 원본 UTF-8 바이트, 저장된 크기, 해시와 Feature를 대조한다. 중복 JSON 키·비정상 숫자·필드 바꿔치기·정해지지 않은 추가 필드·임의 패딩을 정상 자료로 인정하지 않는다. 실제 센서나 기기 값을 사용하고 누락 필드를 합성하지 않는다.

- ESP32의 정수 표현 범위는 `sequence` 1~4,294,967,295, `uptime_s` 0~4,294,967초, `free_heap` 0~4,294,967,295B, `rssi` -128~127dBm이다. 이는 현재 펌웨어·SDK의 표현 범위이며 정상 신호 세기나 공격 판정 경계가 아니다. 크기는 문자열 자릿수와 실제 필드에 따라 바뀌므로 55B나 이번 최대 83B를 정상 고정 크기로 삼지 않는다.
- Pico의 uptime은 밀리초이며 ESP32는 초다. 센서 수치의 유효성 검사는 기존 검증기와 BME280 범위(온도 -40~85°C, 습도 0~100%, 기압 300~1100hPa)를 유지한다. 이 넓은 센서 유효 범위는 센서 데이터의 품질 기준이며 보안 공격 판정이나 실내 환경의 정상 분포를 뜻하지 않는다. [Bosch BME280 자료](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bme280-ds002.pdf)
- 모든 기기에 공통 100B 학습 필터를 적용하지 않는 방향으로 공식 편입을 구현한다. 기기·Profile·정규 메시지 형식·설치 규격으로 선택하고 이전 필터 결과는 재현 가능하게 보존한다.
- 현재 복원된 ESP32 v1은 전송 한도 100B/MQTT 버퍼 256B다. PR 107의 시험 설정은 전송 한도 128B/버퍼 256B이며 기본 P0/P1의 정규 직렬화 최대 65B, P2/P3는 100B를 빌드에서 확인한다. Pico의 5,120B는 펌웨어의 안전 전송 상한이다. 이런 자원 보호 상한을 정상 학습 크기의 상한이나 Rule 경곗값으로 그대로 사용하지 않는다.

## 송신·도착·손실의 판정

예약 간격, Payload의 uptime 차이, Gateway 도착 간격은 서로 다른 값으로 기록한다. ESP32 uptime은 초 정밀도이므로 Payload만으로 정확한 예약 ms를 인증할 수 없다. P1은 실제 Boot 설정·Serial의 `interval_ms`와 성공 송신을 대조하며, 경계 시각의 불확실성을 별도로 남긴다.

ESP32 순번은 로컬 publish 성공 뒤 증가하고 Pico 공개 코드는 샘플 시도마다 증가한다. Pico 순번 공백은 센서 실패·송신 실패·수신 손실을 구분해 조사한다. QoS 0의 로컬 publish 성공은 Gateway 수신 보장이 아니므로 실제 원본 수신을 별도로 대조한다. [MQTT 3.1.1 §4.3.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/errata01/os/mqtt-v3.1.1-errata01-os-complete.html)

첫 안정 정상 후보에서는 구간 내부 순번 공백·중복·uptime 역전·재시작·송신 오류·설명되지 않은 원본 불일치를 HOLD한다. 그 사유는 수집 품질 또는 증거 부족이며 자동으로 공격 라벨을 붙이지 않는다. 허가된 재접속·업로드·진단 구간은 별도 개발 자료로 남긴다.

현재 후보 QC의 sender 4~8초/중앙값 4.5~6.5초, 도착 3~10초, 5분마다 최소 58건, 양 끝 10초 조건은 **기존 P0 중심의 개발 검사**다. Pico 기본 검증기도 같은 sender·도착 검사를 수행한다. 운영 Rule이나 최종 정상 허용 경계로 채택한 수치는 아니다. P0 본 수집 준비에서는 기존 검사를 유지하고, 위반 근거를 보존한다.

P1이 5분 내내 6초로 전송하면 이상이 없어도 약 50건이며, 4초로 전송하면 중앙값 4초다. 현재 QC의 고정 건수·중앙값은 이를 거부할 수 있다. 따라서 P1 예비 Run의 PASS로 4~6초 전체 지원을 선언하지 않는다. 종민의 새 QC는 Profile과 실제 송신 성공·Gateway 대조, uptime 정밀도, 구간 경계에 근거해야 한다. 최저 4초/최고 6초 지속, 섞인 주기, 실제 누락·중복·재시작을 각각 검사하고 원본 검사 결과를 덮어쓰지 않는다.

도착 간격이 흔들려도 순번·송신 uptime·PCAP의 실제 도착을 함께 확인한다. 도착 4~6초를 일괄 정상 조건으로 적용하지 않는다. 기존 QC 위반을 단순히 정상으로 바꾸거나 단일 메시지 Window의 Feature 대체값 5.0초로 실제 송신을 판단하지 않는다.

## 현재 개발 근거

각 Run은 180초이고 같은 Session 108의 한 개발 그룹이다. 봉인 Snapshot·원본·Feature 해시를 다시 대조했다. 아래는 관측값이며 탐지 상한이 아니다.

| Run | ESP32 1 | ESP32 2 | Pico |
| --- | --- | --- | --- |
| P0 | 36건·55B·도착 4.963~5.035초 | 36건·55B·4.965~5.037초 | 35건·128~130B·4.727~5.327초 |
| P1 | 36건·55B·4.975~5.026초 | 36건·52~53B·4.078~5.846초 | 35건·128~130B·4.860~5.200초 |
| P2 | 36건·55B·4.980~5.018초 | 36건·52~83B·4.984~5.013초 | 36건·127~130B·3.501~6.462초 |

P1의 ESP32 2는 10초당 1회/2회/3회 Window가 각각 2/14/2개였다. P0의 Pico도 1회·3회 Window가 있었다. 10초당 정확히 2회를 필수 정상 조건으로 정하지 않는다. P2 Pico의 sender uptime 간격은 5.028~5.034초였고 순번 누락은 없었다. 메시지가 도착한 시각과 센서가 보낸 주기를 구분하는 개발 근거로 사용한다.

이 세 Run의 INBOUND Packet 관측 최대는 약 0.504pps·65.612B/s였다. TCP 제어·연결 상태와 실제 Capture 시간의 영향을 받는 값이며, 단기간 최대값에 임의 배수를 곱해 공격 탐지 경계를 정하지 않는다. 과거 150분 자료와 이 개발 자료는 출처와 사용 이력을 분리한다.

## Rule·학습과 연결

현재 기기별 Rule revision과 Packet 공통 Rule 수치는 유지한다. `expected_publish_interval_seconds`는 현재 정책 설명값이며 자체적으로 송신 주기를 비교하는 Rule이 아니다. MQTT 발행 수·Payload, Packet pps·B/s의 실제 비교 연산과 현재 효력 revision을 기록한다. 새 정상 조건에 맞추기 위해 모든 Rule 상한을 크게 올리거나 이상 행을 지우지 않는다.

이번 P0/P1/P2의 시작 Snapshot은 ESP32 각 revision 1, Pico revision 2다. 당시 세 기기 정책은 예상 주기 5초, 발행 수 15회/10초, Payload 5,120B, Packet 10pps·2,500B/s였다. 이 값은 해당 시점의 운영 Rule 근거이며 새 정상 허용 범위를 뜻하지 않는다. 과거 150분 자료의 같은 값도 별도 과거 근거로 관리한다. 실행 직전에는 실제 최신 효력 revision을 다시 확인한다.

Rate의 float 경계 오차와 Broker DoS 지표의 의미 문제는 P9-08에서 수정·회귀한다. 정상 최대값, Rule 상한, 펌웨어 상한, API 입력 범위를 같은 숫자로 맞추지 않는다. P1/P2·정상 재접속과 필수 공격의 전후 결과를 현수가 검토해 새 Rule revision 또는 공통 정책 버전을 제안한다.

첫 본 Train 후보는 독립 실제 그룹 T1·T2 각 60분, 기본 P0 세 기기로 준비한다. T3는 다양성·품질 부족 때 추가한다. 개발 Validation V1·V2 각 45~60분은 Train과 다른 그룹으로 배정한다. 시간은 시작 규모이며 행 수만으로 적합성을 판단하지 않는다. P1/P2를 학습에 추가할 때는 별도 그룹·Profile 효력·기기별 규격과 공식 QC를 먼저 연결한다.

같은 Session의 기기·MQTT/Packet·Run·프로필을 서로 다른 Split으로 나누지 않는다. 개발에 사용한 자료는 최종 Holdout에서 제외하고 전처리는 Train에서만 학습한다. 이는 현재 프로젝트의 그룹 분할 규칙이며, 그룹 분리·전처리 누수 방지의 근거는 [scikit-learn 그룹 검증](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data)과 [전처리 누수 방지](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)를 따른다.

후보 수집 자체는 현재 경로로 가능하지만 공식 MQTT 100B 필터·Packet의 ESP32 중심 규격·혼합 기기 승인 계약·Profile별 QC는 아직 보완 작업이다. Pico 공개 6파일의 현재 설치 해시는 [후속 설치 확인](phase9-pico-source-evidence.md)에서 일치를 확인했다. 런타임·비공개 설정과 이전 수집 시점 전체를 인증한 것으로 확대하지 않는다. 기준 선택을 이 기술 준비의 완료나 모델 학습 승인으로 표시하지 않는다. 담당자의 사전 결재 없이 기준을 공유해 진행하되, 출처·QC·독립 그룹·실제 Export 선택 범위가 검증된 자료에만 별도 편입 기록을 만든다.
