# 확인된 패킷 공백의 미검사 기록과 탐지 재개

`PACKET_CONFIRMED_GAP_POLICY_ENABLED=true`이면 필수 Packet Rule·IF가 같은 경계에서
대기할 때 확정된 미수집만 `packet_detection_gaps`에 `UNINSPECTED`로 기록한다.
기본값은 false이며 Migration 016이 필요하다.

대상은 바로 다음 같은 인터페이스 Session에 기록된 수집 공백과, 실제 Capture가
시작되지 않은 정확한 10초 `FAILED/LATE_CAPTURE`다. 다음 Session의 첫 정상 특징
구간까지 준비돼야 한다. READY, 정상 미처리 자료, 알 수 없는 실패, 겹침, 중간
Session, Rule·IF 경계 불일치는 자동으로 넘기지 않는다. 기존 PARTIAL_CAPTURE
복구 절차는 그대로 사용한다.

두 Packet 처리 경계와 감사 한 건은 같은 SQLite 트랜잭션에서 저장한다.
AI Runtime Evidence가 활성화되어 있으면 기존 Packet AI 경고 구간도 같은 트랜잭션에서 중단하며, 공백을 추론 완료 기록으로 만들지 않는다.
각 detector의 자료 ID, 원본 실패 상태와 파일은 보존한다. 이후 기존 Orchestrator가
공백의 MQTT·Trust 처리를 먼저 끝내고 정상 패킷 입력을 처리한다. 공백을 정상이나
공격 없음으로 표시하지 않으며, 실패한 수집을 학습 적격 자료로 바꾸지 않는다.
트랜잭션 실패 시 전체 원복되고, commit 이후 재시작은 동일 감사에서 계속한다.
감사 생성 후 옵션을 꺼도 이미 기록된 경계의 catch-up은 마무리할 수 있다.

공백마다 백업·서비스 중단·개별 승인을 실행하지 않는다. 정상 처리 중에는 공백
쓰기 경로를 호출하지 않는다. 운영자는 `PACKET_UNINSPECTED_GAP` 경고와 감사표에서
시작·끝·원인을 확인하고, 반복되는 수집 실패 원인은 별도로 해결해야 한다.

## 배포와 검증

기존 부분 적용은 먼저 실제 감사를 확인해 미완료 detector만 정리한다. 이미 적용된
감사나 실패 자료를 다시 쓰지 않는다. 코드·Migration 016 설치 후 옵션을 활성화하고
Packet Rule·IF, MQTT, Trust의 경계가 순서대로 전진하는지 확인한다. 016의 SQL은
001~011 스키마에도 독립적으로 적용 가능하다. 별도 운영 정비에서 016만 적용할 때는
기존 migration runner의 단일 migration 트랜잭션을 사용하며 012~015를 암묵적으로
실행하지 않는다. 저장소에는 정식 012~015 SQL을 함께 유지하여 전체 runner의
번호 연속성을 보존한다.

검증 기준은 원본 실패 보존, 미검사 감사 1건, 정상 자료 무누락, 공백 뒤 공격의
Trust 반영, 새 수집과 센서 수신 유지다. 예상하지 않은 입력 변경·정합성 오류가
나면 자동 전진하지 않는다. 롤백할 때는 먼저 옵션을 비활성화한다. 새 코드를
유지한 채 이미 기록된 공백의 MQTT·Trust catch-up을 마무리하고 모든 필수 탐지기와
Trust 경계가 마지막 감사의 끝에 도달했는지 확인한 뒤 이전 코드로 복귀한다.
구버전은 새 감사를 읽지 못하므로 catch-up 중간에는 복귀하지 않는다. 기록된 감사와
처리 경계는 삭제하거나 되돌리지 않는다.
