# Packet Rule → IF recovery manager (Phase 9 follow-up)

This one-shot Linux administrator command manages processing-service stop and restoration around the existing audited pair engine. It supports the existing approved `COMPLETED → RUNNING` live-resume path and the core engine's narrow uncaptured `FAILED` tail path when the original pair dry-run explicitly includes `--allow-failed-current-session`. It also accepts an explicitly planned `bounded-replay` pair to consume the immediately following fully ready COMPLETED Session before moving to a later live Session; see [the pair contract](phase9-packet-pair-recovery.md#종료된-정상-구간-재처리). It is not the full P9-05 implementation: generic FAILED-tail recovery, a management HTTP API, per-detector deadlines, automatic model changes, rollback, and an operating-system watchdog are not implemented.

The FAILED source exception accepts only the core engine's single final uncaptured ten-second `LATE_CAPTURE` segment at each consumed checkpoint boundary. A recorded PCAP filename (including a missing file), actual capture, packets or feature rows is rejected. The source Session and failed segment remain unchanged. The flag and each child's evidence are bound by the original pair SHA; the manager keeps that SHA and cannot enable or alter the flag at apply/status/verify time. Child execution uses `APPLY-PACKET-FAILED-TAIL-LIVE-RESUME`. Rule-only completion resumes the original IF under the same audits and CAS. Target readiness, fresh Rule/IF/Trust advances and all other completion gates remain the same. This is not generic FAILED recovery.

Run from the approved repository root, using the same Python environment, `.env`, stage settings, Capture policy and custom runtime lock paths as the services. Use the existing pair dry-run to create a fresh approved pair plan first. All paths below refer to new files/directories under the repository's ignored `output/` or another approved artifact directory; create their parent directories beforehand. Do not overwrite tracked source files or use symlinks/junctions.

```text
python -m edge.detection.run_packet_recovery_pair plan \
  --pair-plan-file output/pair-plan.json --db-path backend/data/iot_security.db \
  --artifact-dir output/recovery-artifacts --plan-output output/manager-plan.json
```

`plan` reads the DB, repository and exact state of the three processing units, then writes only the new manager plan. It performs no DB or service mutation and does not require root. The plan binds the pair SHA, database, source/target sessions, repository, Boot ID, service units and fixed time budgets. Confirm its SHA after reviewing the existing pair's administrator, reason, skip approval and before/after checkpoints. A pair artifact group that already exists without a manager original-state journal is blocked; its original service states cannot be inferred safely.

```text
sudo <service-python> -m edge.detection.run_packet_recovery_pair apply \
  --plan-file output/manager-plan.json \
  --confirm APPLY-PACKET-PAIR-MANAGER:<manager-plan-sha256>
```

`apply` requires root on Linux. It holds a separate per-database command lock, records the immutable original service states before launching, and starts a detached supervisor with no inherited terminal input/output. The caller can disconnect. A repeated invocation returns the existing running operation rather than starting a second one. PID plus Linux start identity, attempt ID, role and worker nonce identify each launch. An unresolved launch without a proved receipt is held for inspection instead of retried automatically. The supervisor waits up to 15 seconds for the launcher's command lock to release, then retains that lock throughout management and verification.

Only `packet-feature-extractor.timer`, `detection-orchestrator.service` and `packet-feature-extractor.service` are stopped, in that order. Capture and MQTT Subscriber keep running. The manager does not stop arbitrary manual runners; they must use the same approved runtime lock paths and relinquish them before application. The worker acquires the existing pair's union of Orchestrator/manual/extractor locks once. A busy or differently configured lock cannot be bypassed. A stopped service must be confirmed inactive, and service units must report a clean `Result=success`/`ExecMainStatus=0`; an unclean stop causes HOLD.

The default budgets recorded in the manager plan remain unchanged: 35 seconds for each stop command, **120 seconds for the entire Rule → IF pair worker**, 5 seconds for TERM/reap, another 5 seconds for KILL/reap, 35 seconds for each restoration command, and the existing v1 key verify_observation_start_seconds=120. The manager schema, signed budgets, timeout scope and pair/child approvals are preserved. Final verification now runs in a fresh owned process: the supervisor gives each observation only the remaining part of that 120-second window, and the standalone verify command uses the same bounded path. A timeout, damaged/stale response, late completion or unconfirmed child shutdown returns APPLIED_VERIFY_HOLD; after safe service restoration this path never stops services or applies Rule/IF again.

The observation window excludes shutdown cleanup, which can use the additional TERM/reap and KILL/reap budgets (default at most ten seconds). Direct child reap and absence of live members of its owned process group are recorded separately. A reaped leader with a surviving TERM-ignoring descendant still requires KILL and bounded shutdown confirmation. Linux start identity and session/group membership prevent signalling a reused PID/group; zombies are no longer running, while the direct child must still be reaped. A fresh nonce, attempt, approval SHA and process receipt and response checksum bind each verifier's pipe response; historical responses cannot declare completion. A live verifier, pending launch or unconfirmed shutdown blocks another verification or apply. SIGTERM during supervisor or standalone verification requests cleanup; the short spawn/receipt handoff defers TERM/INT until the caller retains the child handle.

This is not an upper bound on the entire management operation. Full planning, pre/post-worker DB reconciliation and repository inspection remain outside the final verification-process deadline; the standalone verify command also retains the full signed-plan, pair/DB/configuration and generated-path validation before any lock/journal writes and before its observation window starts. This preflight can still wait in Git or filesystem inspection and has no separate hard process deadline. Kernel/filesystem stalls, supervisor SIGKILL and a host reboot still require external inspection and are not covered by an OS watchdog. Service-state and clean-stop commands retain separate five-second limits. The worker's 120-second deadline remains shared by Rule and IF: per-detector deadlines and a new manager schema are follow-up work, not part of this change. Process exit or missing stdout/result files alone never prove a commit or successful recovery.

At startup and after child exit, the manager reconciles the actual DB with the original approved pair. It checks the deterministic child IDs, full audit fields and plan JSON, before/after checkpoint, target identity, current Boot/configuration, repository state and actual backup path/hash/sidecar. Backup integrity/FK and the approved before checkpoint are read using read-only SQLite snapshots; the backup SHA must remain unchanged across verification. It does not adopt another recovery's audit.

- A confirmed absence of both commits permits restoration of original active units.
- Both complete, verified DB audits permit restoration of original active units. This means the checkpoint changes were applied, not that runtime progress has completed.
- Rule-only application, uncertain audit/checkpoint state, a live or unreaped child, or a missing original-state journal keeps processing services stopped. Reapplying the same manager plan preserves the original service states and resumes only the unfinished IF using its original CAS.
- A restoration failure preserves the applied audits and records HOLD. Reapplying a resolved operation can retry restoration using the original journal; it never replaces original active states with the currently stopped states.

Restoration uses the original active units only, in reverse stop order. Originally inactive units remain inactive. The journal separates immutable `original`, latest `requested`, observed `actual`, a durable transition history and `restoration_failures`. Each request is flushed before its service command; each actual outcome is recorded afterward. A failure does not erase earlier attempts. Manager files are under `manager-<manager_id>/` in the artifact directory. Existing pair files remain under `<pair_id>/`: child plans are under `attempt-*/<detector>/plan.json`, while backup/checksum/child result are under the deterministic child ID.

```text
python -m edge.detection.run_packet_recovery_pair status --plan-file output/manager-plan.json
python -m edge.detection.run_packet_recovery_pair verify --plan-file output/manager-plan.json
```

`status` reads actual services, process receipts, full DB audits and checkpoints. It does not control services, write the manager journal, or call the existing progress writer. Its `last_verification` is historical; full application is reported as `APPLIED_VERIFY_REQUIRED` until a fresh verification is performed. `verify` first rejects a live worker, a recorded restoration failure or an unconfirmed original active service; it performs no service control but intentionally updates the existing pair's `progress.json` under its progress lock. The supervisor polls verification after safe restoration, using the remaining hard observation window described above. Completion still requires the existing pair gates: same Boot/target and configuration, active required services, eligible contiguous Capture/Feature data, no new FAILED segment, synchronized clock, fresh Rule/IF/Trust boundaries within 45 seconds, actual consumption and two observed advances. A held verification can be retried without executing already applied children.

Successful planning and freshly verified `COMPLETE` or `REPLAY_COMPLETE` return exit 0. For bounded replay, fixed input/hash and actual Packet/MQTT/Trust completion at the preserved end replace live freshness and two-advance gates. `REPLAY_COMPLETE` never declares the later running Session recovered; it requires a separate live plan and approval. Confirmed uncommitted non-completion returns 2; asynchronous launch, partial/uncertain application, restoration failure and applied-but-unverified progress return 3. An asynchronous `apply` exit 3 is not a declaration that the background operation failed; inspect `status` and then `verify`. Never treat `RUNNING` or two applied audits alone as complete recovery.

SSH/client disconnect is covered by the detached supervisor. Host reboot, supervisor SIGKILL, kernel/filesystem failure or external service changes are not covered by an OS watchdog: unresolved launch/live-child/changed-Boot states remain HOLD and require administrator inspection. The command does not guess legacy original states or automatically kill a worker that it cannot identify. Deployment and tests against real services/operational databases have not been performed.
