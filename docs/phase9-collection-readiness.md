# Phase 9 본 수집 준비

2026/10/9 기준 준비 항목이다. 현재 후보 수집은 가능하지만 세 기기 공식 편입·학습 승인은 준비 중이다. 이 문서는 수집 실행이나 승인 기록을 대신하지 않는다. 예비 시험의 메시지 규격은 [메시지 규격](phase9-message-contract.md), 원본 보존·QC는 [후보 수집 절차](phase8-normal-collection.md)를 따른다.

## 본 수집 전 확인

| 담당 | 먼저 확인할 항목 | 남길 결과 |
| --- | --- | --- |
| 우민 | 기기별 정상 Profile, 실제 설치 증거, 수집 그룹·보존 공간, 실행 직전 운영 상태 | 설치/수신 근거, 그룹 배정표, 수집 시작 또는 보류 기록 |
| 종민 | 세 기기 공식 편입, 원본·Feature 선택 범위, 품질·출처·해시·그룹 검사, 별도 승인 기록 | 편입·QC 계약과 검증, 포함/제외 사유, 최종 Snapshot 연결 |
| 현수 | 정상 운용 기준 v1, Rule 경계·AI 관찰 해석, 활성 처리 단계 | 판정 계약, 경계·공격 회귀 계획, 운용 조건 수정 필요성 |

정상 운용 조건은 [정상 운용 기준 v1](phase9-normal-operating-range.md)로 먼저 정했다. 첫 본 수집 후보는 세 기기 기본 동작 P0다. P1·P2는 허용된 개발 Profile이며 Profile별 QC·혼합 기기 공식 편입·독립 그룹 검증 뒤 학습 포함을 결정한다. P3와 재접속은 별도 개발 시험이다. 종민·현수의 사전 결재를 기다리지 않고 우민이 기준을 공유해 준비를 진행한다. 예비 QC PASS나 탐지 이벤트 부재는 자료의 학습 승인이 아니다.

현재 후보 Export는 Pico 원본을 보존하지만, 기존 공식 MQTT Export의 100B 고정 선택과 Packet Importer의 옛 ESP32 규격 제한은 남아 있다. 세 기기 자료를 기존 공식 경로에 그대로 넣어 학습할 수 있다고 가정하지 않는다. 긴 수집 전에 정상 조건·출처·그룹과 공식 편입의 실제 선택 범위·QC·승인 방식이 준비돼야 한다. 모델 생성·배포와 평가 도구 전체 완료까지 먼저 요구하는 조건은 아니다.

## 그룹 배정 초안

| 슬롯 | 용도 | 시간 | 조건 |
| --- | --- | --- | --- |
| T1·T2 | Train | 각각 60분 | 세 기기 동시 관측, 서로 다른 실제 원본 그룹 |
| T3 | 추가 Train | 필요 시 60분 | 자료 다양성·품질 검토 후 결정 |
| V1·V2 | 개발 Validation | 각각 45~60분 | Train과 서로 비중복인 실제 원본 그룹, 실행 전 시간 확정 |

각 슬롯의 실제 Session UUID는 생성·재개 검증 후 기록한다. 같은 그룹의 MQTT·Packet·다른 기기·다른 Run을 서로 다른 Split으로 나누지 않는다. V1·V2는 개발용이며 Phase 10 최종 Holdout은 모델·기준 동결 후 새로운 그룹으로 수집한다.

## 실행 순서

1. Session 108에서 펌웨어 확인·조정과 짧은 예비 점검을 마친다. 정상 Profile과 편입 선행 기준을 고정하고 Commit·설정·모델/Stage·등록 IP·정책 Revision·Trust·시간 동기화·공간을 기록한다.
2. 기존 계획 종료 도구의 검사와 `prepare-stop`으로 현재 Capture와 수락된 MQTT 입력을 마감한다. 필수 처리 경계 drain과 **READY**를 확인하고 OS를 정상 재부팅한다. 종료 도구 자체가 OS를 재부팅하지는 않는다.
3. 새 Boot의 시간 동기화, 정확히 하나인 새 RUNNING Session과 적격 Feature를 확인한다. 기존 `resume`의 승인·백업·무결성·Source/Target 검사와 두 차례 처리 전진 검증을 통과한다.
4. 새 Session UUID를 사전 배정 슬롯에 연결한다. 새 출력 폴더에서 `edge.features.collect_normal_candidate`로 세 기기의 미래 10초 경계 구간을 수집한다. 수집 중 배포·정책 변경·공격·격리·복구 시험을 병행하지 않는다.
5. 후보 QC·원본·`after.db`를 보존한다. 이 Snapshot의 Session은 RUNNING일 수 있다. 다음 계획 종료 때 최종 COMPLETED Snapshot·종료 감사·READY를 **별도로** 연결하고 원본 Manifest는 변경하지 않는다.
6. 종민이 실제 공식 Export 대상 전체 또는 구현·검증된 승인 구간을 QC한다. 시작 안정화·재개 대기·종료 구간을 자동 제외했다고 가정하지 않는다. 선택 범위·품질·출처·그룹이 충족되지 않으면 HOLD한다.
7. 다음 슬롯도 새 Boot·새 Session과 같은 검증을 거친다. 같은 Boot에서 Capture만 재시작하는 경로는 기존 정상 재개가 거부하므로 사용하지 않는다.

현재 후보 도구는 활성 처리 단계 6개를 고정 대기한다. MQTT IF 활성화 등 실행 구성이 바뀌면 실제 활성 단계의 종료 경계를 기다리는 동작을 먼저 보완·검증한다. 최소 1GiB라는 도구 요구량과 별도로 모든 그룹의 DB 사본·PCAP·백업·검토 사본 보존량을 산정한다.

## 지금까지의 자료와 미확인 항목

- Session 108 / `2e72eab6-b8eb-4b5a-873e-3599b932f0e1`은 P0·P1·P2와 펌웨어 조회·복원·진단이 포함된 개발 그룹이다. 전체 안정 정상 Train/Validation으로 승인하지 않는다. 후보의 학습·전체 Session 승인 false는 유지한다.
