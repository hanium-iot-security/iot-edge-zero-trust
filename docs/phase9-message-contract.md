# 세 기기 메시지 규격과 예비 수집

2026-10-09 P0 기본 점검과 P1·P2 예비 수집에서 확인한 규격이다. 관측 크기·수신 간격은 이번 시험의 값이며 최종 정상 허용 범위나 Rule 경곗값이 아니다. 수집 결과는 [예비 수집 검증 기록](phase9-normal-pilot-results.md), ESP32 설정·빌드·실행은 [펌웨어 사용 절차](phase5-normal-firmware-runbook.md)를 따른다.

## 메시지 형식과 단위

Topic은 `iot/{device_id}/sensor`이며 본문의 `device_id`와 일치해야 한다. 기기별 형식을 보존하고 빠진 센서 필드를 합성하지 않는다.

| 기기·패턴 | 본문 필드 | 단위·순번 의미 |
| --- | --- | --- |
| ESP32 P0·P1 | `device_id`, `sequence`, `uptime_s` | `sequence`는 단위 없는 순번. 송신 측 publish 성공 뒤 증가한다. `uptime_s`는 초 |
| ESP32 P2 | 위 필드와 선택 `rssi`, `free_heap` | `sequence % 3`이 0이면 필수만, 1이면 `rssi`, 2이면 `rssi`·`free_heap` 추가. RSSI는 dBm, Free Heap은 B. 실제 측정값 사용 |
| Pico 기본 | `device_id`, `seq`, `uptime_ms`, `temperature_c`, `humidity_pct`, `pressure_hpa` | `seq`는 단위 없는 순번, 가동시간은 ms, 온도는 °C, 습도는 %, 기압은 hPa |

Pico의 공개 저장소 코드에서는 샘플 시도 때 `seq`를 증가시켜 센서·송신 실패 시 순번이 건너뛸 수 있다. ESP32의 성공 후 증가와 같게 해석하지 않는다. 후속 조회에서 현재 공개 앱·라이브러리 6파일의 설치 해시가 저장소와 일치함을 확인했다. [설치 확인 기록](phase9-pico-source-evidence.md)은 현재 공개 소스의 근거이며 비공개 설정·런타임 전체·과거 수집 시점을 소급 인증하지 않는다. 순번 공백만으로 Gateway 데이터 손실이라고 단정하지 않는다.

QoS 0의 기기 publish 성공은 송신 측 결과다. Gateway 수신은 원본의 기기·Topic·순번·Payload·크기를 대조해 확인한다. `firmware_version`·Profile·소스/빌드 해시는 본문 필드로 추가하지 않고 Manifest와 별도 설치 증거로 연결한다.

## 주기와 관측 크기

| 시험 | ESP32 1 | ESP32 2 | Pico |
| --- | --- | --- | --- |
| P0 기본 점검 180초 | 5초 설정·55B·36건 | 5초 설정·55B·36건 | 기본 약 5초·128~130B·35건 |
| P1 예비 수집 180초 | P0 유지·55B·36건 | 4~6초 예약 설정·52~53B·36건 | 기본 유지·128~130B·35건 |
| P2 예비 수집 180초 | P0 유지·55B·36건 | 5초 설정·52~83B·36건 | 기본 유지·127~130B·36건 |

ESP32 2의 P1 실제 Gateway 수신 간격은 4.078~5.846초, P2는 4.984~5.013초였다. 예약 간격과 실제 수신 간격을 구분한다. P2에서 Pico의 완전한 메시지 도착 간격은 3.501~6.462초였으며 순번 누락은 없었다. 송신·무선 경로 원인은 미확인이다. 단일 메시지 Window에 기존 MQTT Feature가 채우는 5.0초는 실측 간격으로 사용하지 않는다.

ESP32 2의 P1·P2 시험 버전은 `phase9-normal-pilot-v2`, Payload Schema는 `phase5-normal-payload-v1`, 한도 계약은 `phase9-normal-limits-v1`이다. 최대 Payload 128B·MQTT Buffer 256B는 시험 설정이다. ESP32에 적용한 전송 한도를 Pico의 정상 후보에 일괄 적용하지 않는다. 펌웨어 전송 상한·학습 Export 필터·운영 Rule 상한은 각각 검토한다. 고정 100B 학습 필터의 제거·대체 작업은 아직 별도 데이터 작업으로 남아 있다.

시험 후 ESP32 2는 보존한 원래 v1·P0로 복원했다. ESP32 1은 v1·P0를 유지했고 Pico는 기본 동작을 유지했다. 이 상태는 시험·복귀 확인 시점의 기록이며 이후 설치나 설정 변경 시 새 증거를 연결한다.
