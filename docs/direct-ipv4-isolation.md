# 단일 IPv4 격리 규칙

`FIREWALL_AUTO_SCOPE=PI_INPUT_IPV4_ALL`에서는 이후의 최초 격리부터 해당 기기 → Pi INPUT의 모든 IPv4 포트·프로토콜을 규칙 한 개로 차단한다. MQTT 선행 규칙과 다음 주기의 자동 확장은 생성하지 않는다. 다른 기기, 다른 호스트 간 통신, FORWARD와 IPv6는 차단 범위에 포함되지 않는다.

## 처리와 복구

1. 기존 Rule 감점으로 Trust가 30 미만이 되면 격리 결정과 광역 PENDING 규칙을 같은 DB 트랜잭션에 기록한다.
2. Worker가 현재 정책·IP·격리 상태와 감점 근거를 다시 확인한 뒤 정확한 ID의 규칙을 적용한다. PENDING은 실제 차단 완료를 뜻하지 않는다.
3. 관리자가 해당 규칙의 해제를 요청한다. Worker가 정확한 규칙을 삭제하고 실제 부재를 확인해야 REMOVED와 성공 감사를 남긴다.
4. 대시보드에서 사전 점검 후 정상·100점 복구를 실행한다. 미해결 규칙이나 실제 잔여 차단이 있으면 복구하지 않는다.

신뢰점수 감점·격리 기준과 AI 관찰 정책, 모델·임계값은 그대로다. 전체 IPv4 규칙의 protocol·port는 NULL이며 화면에는 ‘전체 IPv4 / 모든 포트’로 표시한다.

직접 규칙은 `source_rule_id=NULL`, `requested_by=system:trust-score-v2`와 실제 대표 감점 이벤트를 기록한다. 과거 MQTT 규칙과 확장 규칙은 ID·연결·해제 이력을 유지한다. 과거 두 규칙이 실제로 남아 있으면 각각 해제해야 한다. 이력 창에서는 같은 격리 결정의 부모·확장 규칙을 함께 표시한다.

같은 기기나 출발지 IP의 PENDING·APPLIED·FAILED 규칙 또는 해제 대기가 남아 있으면 새 직접 규칙을 적용하지 않는다. 과거 기록이나 CLI 해제로 REMOVED 행에 현재 방식의 해제 감사가 없으면, Worker가 해당 ID의 정확한 규칙이 실제로 없는지 먼저 확인한다. MQTT·광역 모두 같은 확인을 거친다. 잔여 규칙이 있거나 확인할 수 없으면 적용을 중단한다. 옛 행을 수정하거나 과거 해제 감사를 새로 만들어 넣지 않는다.

## 적용과 되돌림

- Migration 018은 기존 방화벽 행·참조·삭제된 ID의 상한을 보존하며, 직접 광역 규칙을 저장할 수 있도록 CHECK 제약을 확장한다. 큰 변경 전에는 검증된 전체 백업을 확보하고 운영 DB 사본에서 먼저 적용한다.
- Trust를 실행하는 Orchestrator와 Firewall Worker 코드를 함께 반영하고 정상 재시작한다. 이전 Worker는 부모 없는 광역 규칙을 처리할 수 없다. API도 최신 migration runner를 사용해야 한다.
- `FIREWALL_AUTO_SCOPE`는 이후 생성에만 적용된다. 새 코드에서 MQTT 값으로 되돌려도 저장된 광역 규칙의 정확한 해제·복원을 유지한다.
- 코드 되돌림에도 migration 018을 인식하는 runner와 직접 규칙 처리 코드를 유지한다. 운영 중인 규칙 ID 위에 과거 DB를 덮어쓰지 않는다.
- 수집 서비스·펌웨어·AI 설정은 이 변경의 배포 대상으로 포함하지 않는다. 실기 차단 시험은 별도 검증 결과와 구분한다.
